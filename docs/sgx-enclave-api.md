## Overview

- **Port**: Environment variable `SGX_HTTP_PORT`, defaults to `3000`
- **Base URL**: `http://localhost:3000`
- **All endpoints use `POST`**, Content-Type: `application/json`
- **20 endpoints in total** (challenge values are provided uniformly by `/api/challenge`)

---

## Common Request Format

Except for `/api/enclave/info`, the HTTP body of all endpoints is:

```json
{
  "payload": "<JSON string>",
  "platformSignature": "<EIP-191 secp256k1 signature>"
}
```

- `payload`: JSON string (type string, not object). Each endpoint parses the payload into different fields; see the **payload field definitions** for each endpoint.
- `platformSignature`: Platform's EIP-191 `personal_sign` signature over `payload`. Hex format with `0x` prefix, 132 characters. The server recovers the signer address via `ethers.verifyMessage(payload, platformSignature)` and verifies whether that address is in the on-chain whitelist contract.

After signature verification, the server executes `request = JSON.parse(payload)` and subsequent business logic reads fields from the parsed object.

**Common curl request example**:

```bash
curl -X POST http://localhost:3000/api/<endpoint>   -H "Content-Type: application/json"   -d '{
    "payload": "{\"field1\":\"value1\",\"field2\":\"value2\"}",
    "platformSignature": "0xabc123...signature_hex"
  }'
```

---

## Common Response Format

All endpoints return a uniform HTTP response:

```json
{
  "attestationQuote": "<SGX quote hex string>",
  "data": "<JSON serialized string of handler return value>"
}
```

- `attestationQuote`: SGX remote attestation quote, generated by computing SHA256 of the `data` field and injecting it into `user_report_data`. Empty string in non-SGX environments.
- `data`: JSON string of the handler return value; the client must deserialize it with `JSON.parse(data)`.

**Error Response** (HTTP 400/401/404/500):

```json
{ "error": "Error description" }
```

**HTTP Status Codes**:

| Status Code | Meaning |
|-------------|---------|
| 200 | Request processed successfully |
| 400 | Missing or malformed request parameters |
| 401 | Platform signature verification failed or WebAuthn authentication failed |
| 403 | Account is frozen (security protection mechanism) |
| 404 | Resource does not exist |
| 500 | Internal server error |

## WebAuthn Signature Format

The `webauthnSignature` field structure used in the endpoints below (Browser WebAuthn API assertion response format):

| Sub-field | Type | Description |
|-----------|------|-------------|
| `authenticatorData` | string | Authenticator data, base64url encoded |
| `clientDataJSON` | string | Client data JSON, base64url encoded (includes challenge, origin, etc.) |
| `signature` | string | P256 signature, base64url encoded (DER format) |

> **Note**: The `challenge` field does not need to be passed separately; the server automatically extracts and validates it from `clientDataJSON`.

## 1. POST /api/challenge

**Unified challenge interface**. All operations that require a WebAuthn signature obtain a challenge value through this interface. The verification logic and returned content depend on the `purpose` field.

### Challenge Security Mechanism

**Full flow** (for non-`register` purposes):

**Step 1**: Call `/api/challenge` to get `rawChallenge` (pure random value)

```
// payload
{ "purpose": "wallet_create", "userId": "user-xxx", "credentialId": "cred-xxx" }
// response data
{ "challenge": "rawChallenge_base64url", "userId": "user-xxx", "expiresAt": "..." }
```

**Step 2**: The client constructs `userIntentJson`, computes `intentHash`, and signs with Passkey

```
userIntentJson = JSON.stringify({ purpose, userId, ...business parameters })
intentHash = SHA256(rawChallenge + userIntentJson)
webauthnSignature = Passkey.sign(intentHash)
```

**Step 3**: Call the business endpoint carrying `rawChallenge + userIntentJson + webauthnSignature`

```json
// payload (wallet/create example)
{
  "userId": "user-xxx",
  "credentialId": "cred-xxx",
  "rawChallenge": "rawChallenge_base64url",
  "userIntentJson": "{\"purpose\":\"wallet_create\",\"userId\":\"user-xxx\",\"chains\":[{\"chainId\":\"1\"}]}",
  "webauthnSignature": { "authenticatorData": "...", "clientDataJSON": "...", "signature": "..." },
  "chains": [{ "chainId": "1" }]
}
```

**Server-side verification flow** (business endpoint):

1. Query the challenge record by `rawChallenge`; reject if it does not exist (replay protection)
2. Compute `intentHash = SHA256(rawChallenge + userIntentJson)`
3. Verify WebAuthn signature (`expectedChallenge = intentHash`)
4. Parse `userIntentJson` and compare fields one by one with actual business parameters (prevent platform parameter substitution)
5. Consume (delete) the challenge record

> **Note**: The WebAuthn challenge for the authorization JSON (`authorizationJson` field in `/api/tx/sign`) is computed by the client itself (`SHA256(authorizationJson)`); the `/api/challenge` interface is not required.

**Payload Field Definitions**:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `purpose` | string | Yes | Operation purpose (see enum below) |
| `userId` | string | Depends on purpose | `register` is optional (auto-generated if omitted), required for other purposes |
| `credentialId` | string | Required when not `register` | Passkey credential ID (base64url encoded), used to verify Passkey ownership |

`purpose` enum values:

| Value | Corresponding Operation | Requires Passkey Ownership Verification |
|-------|-------------------------|----------------------------------------|
| `register` | New user Passkey registration | No (userId optional) |
| `register_passkey` | Existing user adding a new Passkey | Yes |
| `wallet_create` | Create wallet | Yes |
| `wallet_delete` | Delete wallet container | Yes |
| `passkey_delete` | Delete Passkey | Yes |
| `wallet_entry_delete` | Delete a single logical wallet | Yes |
| `key_export` | Key export initialization | Yes |
| `key_export_confirm` | Key export confirmation (authorize wallet deletion) | Yes |
| `evidence_query` | Evidence query (user-initiated) | Yes |
| `key_import_init` | User-side key import initialization | Yes |
| `key_import_complete` | User-side key import completion | Yes |

**`userIntentJson` field specifications for each purpose** (used in business requests, not passed in this interface):

| purpose | userIntentJson required fields | Description |
|---------|-------------------------------|-------------|
| `register_passkey` | `{ purpose, userId }` | Used when an existing user adds a new Passkey |
| `wallet_create` | `{ purpose, userId, chains, mnemonicStrength? }` | `chains` is an array of chain configurations; `mnemonicStrength` is optional |
| `wallet_delete` | `{ purpose, userId, walletId }` | Specify the wallet ID to delete |
| `passkey_delete` | `{ purpose, userId, credentialIdsToDelete }` | Specify the list of credential IDs to delete |
| `wallet_entry_delete` | `{ purpose, userId, walletId, address }` | Specify the logical wallet address to delete |
| `key_export` (ECDH) | `{ purpose, userId, exportInfo, peerPublicKey }` | `exportInfo` is `[{walletId, addresses}]`; empty `addresses` exports all private keys under that walletId; elements can be plain address strings or `{address, chainId}` objects (exact chain match); `peerPublicKey` is the client ECDH public key (hex) to prevent man-in-the-middle substitution |
| `key_export` (RSA) | `{ purpose, userId, exportInfo, rsaPublicKey }` | `exportInfo` is `[{walletId, addresses}]`; empty `addresses` exports all private keys under that walletId; elements can be plain address strings or `{address, chainId}` objects (exact chain match); `rsaPublicKey` is the client RSA public key (raw PEM string) to prevent man-in-the-middle substitution |
| `key_export_confirm` | `{ purpose, userId, sessionId }` | Confirm data received and authorize wallet deletion; `sessionId` prevents substitution |
| `evidence_query` | `{ purpose, userId, authorizationId? }` | Provide `authorizationId` when querying a specific authorization |
| `key_import_init` | `{ purpose, userId, importType }` | User-side import initialization; `importType` prevents platform substitution of import type |
| `key_import_complete` | `{ purpose, userId, sessionId, walletId, chains }` | User-side import completion; `userId` binds to Passkey ownership; `sessionId` prevents session substitution; `walletId`/`chains` prevent platform tampering of storage target and derivation chains (can be null) |

> **Important**:
> - `userIntentJson` is passed in the **business endpoint** payload (not this interface), not here.
> - Values in `userIntentJson` must not be transformed; the server compares them directly with actual request parameters, and rejects any mismatch.
> - For `key_export`, `peerPublicKey`/`rsaPublicKey` must be included in `userIntentJson` to prevent man-in-the-middle substitution of key exchange parameters.
> - `intentHash = SHA256(rawChallenge + userIntentJson)`; the client uses this hash as the WebAuthn challenge for signing.

**`data` field (after JSON.parse)**:

| Field | Type | Description |
|-------|------|-------------|
| `challenge` | string | Base64url encoded pure random challenge value (rawChallenge, TTL 300 seconds) |
| `userId` | string | User ID (server-generated if not provided for `register`) |
| `expiresAt` | string | Challenge expiration time (ISO 8601) |

**Request Example (Passkey registration, no credentialId required)**:

```json
{
  "payload": "{\"purpose\":\"register\",\"userId\":\"user-xxx\"}",
  "platformSignature": "0x..."
}
```

**Request Example (Wallet creation, only userId + credentialId required)**:

```json
{
  "payload": "{\"purpose\":\"wallet_create\",\"userId\":\"user-xxx\",\"credentialId\":\"cred-xxx\"}",
  "platformSignature": "0x..."
}
```

> **Explanation**: The `challenge` returned by this interface is a pure random value (rawChallenge). After receiving it, the client must construct `userIntentJson`, compute `intentHash = SHA256(rawChallenge + userIntentJson)`, sign `intentHash` with Passkey, and finally carry `rawChallenge + userIntentJson + webauthnSignature` in the business endpoint.

## 2. POST /api/passkey/register/complete

Second step of the Passkey registration flow. Submits the response data after the WebAuthn registration ceremony completes; the server uses `@simplewebauthn/server` to verify and extract the COSE public key for storage.

Three scenarios are supported:
- **Scenario A (No Passkey, purpose=register)**: Submit `attestationResponse` directly, using the `purpose=register` challenge value
  - `userId` is optional: if provided, that userId is used; if not, it is retrieved from the challenge record (random userId generated by the challenge interface)
  - Applicable to brand-new users (userId does not exist) or existing accounts without a Passkey
  - ⚠️ **Security enhancement**: If registering for an existing account (userId exists) and the account has wallets (mnemonic or raw private key), the account is automatically frozen (see Appendix E)
  - ⚠️ **Frozen account replacement**: If the account is already frozen, re-registering via `purpose=register` will replace the old frozen Passkey, and the freeze timer resets (default 72 hours, configurable; see Appendix E)
- **Scenario B (Existing Passkey, purpose=register_passkey)**: Also provide `existingCredentialId` + `existingWebauthnSignature`, using the `purpose=register_passkey` challenge value
  - `userId` must be provided
  - ⚠️ Frozen accounts are not allowed to use `purpose=register_passkey`
- **Scenario C (Passkey recovery, purpose=register)**: User lost all Passkeys; Owner authorizes recovery through the contract
  - `userId` must be provided, **without** `existingWebauthnSignature`
  - Precondition: Owner has called `setPasskeyRecovery(userId, newPubKeyHash, oldPubKeyHash, uuid, memo)` in the contract
  - SGX queries the contract to match `(userId, SHA256(newPublicKeyCose))`, verifying `oldPubKeyHash` matches the existing Passkey
  - Keeps the matched old Passkey record, deletes other Passkeys, and replaces the kept record with the new Passkey
  - Automatically triggers account freeze (72h); response includes `recovery=true` and `recoveryUuid`
  - ⚠️ This feature is unavailable when the contract is unavailable

> **Security enhancement**: To prevent attackers from exploiting this backdoor to impersonate a bound Passkey and steal assets, when an existing account (with wallets) binds a Passkey via Scenario A, the system automatically freezes the account (default 72 hours, configurable). See Appendix E.

**Scenario B Security Flow**:
1. Client calls `/api/challenge` (`purpose=register_passkey`) to get `challenge1`
2. Client creates a new Passkey with `challenge1` → obtains `newCredentialId` and `newPublicKeyCose`
3. Client computes `existingChallenge = SHA256(challenge1 + newCredentialId + newPublicKeyCoseBase64url)`
4. Client signs `existingChallenge` with the existing Passkey (`existingWebauthnSignature`)
5. Server verifies both signatures to ensure the new Passkey's public key and ID are not substituted midway

**Payload Field Definitions**:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `userId` | string | Required for Scenario B, optional for Scenario A | User ID. If omitted in Scenario A, retrieved from the challenge record (random userId generated by the challenge interface) |
| `attestationResponse` | object | Yes | WebAuthn registration response (sub-fields below) |
| `existingCredentialId` | string | Required for Scenario B | Existing Passkey credential ID (used for identity verification) |
| `existingWebauthnSignature` | object | Required for Scenario B | Existing Passkey's WebAuthn signature (challenge = SHA256(challenge1 + newCredentialId + newPublicKeyCoseBase64url)) |

`attestationResponse` sub-fields (Browser WebAuthn API registration response format):

| Sub-field | Type | Required | Description |
|-----------|------|----------|-------------|
| `id` | string | Yes | Base64url encoded credential ID |
| `rawId` | string | Yes | Base64url encoded credential ID (same as `id`) |
| `response.attestationObject` | string | Yes | Base64url encoded attestation object (CBOR format) |
| `response.clientDataJSON` | string | Yes | Base64url encoded clientDataJSON (includes challenge, origin) |
| `type` | string | Yes | Fixed as `"public-key"` |

> **Note**:
> - The server extracts `challenge` from `clientDataJSON` and compares it with the challenge value stored in the database (one-time use)
> - The server extracts `origin` from `clientDataJSON` and uses it as `expectedOrigin` and `expectedRPID` (no phishing verification)
> - The public key is stored in COSE format; the client does not need to provide `publicKeyX/Y`
> - In Scenario B, the challenge of `existingWebauthnSignature` is not directly generated by the server; it is `SHA256(challenge1 + newCredentialId + newPublicKeyCoseBase64url)`, so the existing Passkey's signature binds the new Passkey's public key and ID, preventing substitution midway

**`data` field (after JSON.parse)**:

| Field | Type | Description |
|-------|------|-------------|
| `success` | boolean | Fixed `true` |
| `userId` | string | User ID |
| `credentialId` | string | Registered credential ID (base64url) |
| `isFirstPasskey` | boolean | `true` when there was no Passkey under this userId before (including brand-new users and existing accounts without a Passkey) |
| `recovery` | boolean | Optional. `true` means this registration is a contract-authorized Passkey recovery (Scenario C) |
| `recoveryUuid` | string | Optional. Unique identifier of the recovery entry, only returned when `recovery=true` |
| `frozen` | boolean | Optional. `true` means the account has been frozen (Scenario A binding to an account with wallets, or Scenario C recovery) |
| `freezeUntil` | string | Optional. Freeze deadline (ISO 8601 format), only returned when `frozen=true` |

## 3. POST /api/passkey/delete

Delete Passkeys (batch supported). If no Passkeys remain for the user after deletion, all user data is cascaded (wallets, authorization states, etc.).

**Prerequisite Steps**:
1. Call `/api/challenge` (purpose=`passkey_delete`) to get `rawChallenge` (pure random value)
2. Construct `userIntentJson = { purpose, userId, credentialIdsToDelete }`
3. Compute `intentHash = SHA256(rawChallenge + userIntentJson)` and sign `intentHash` with Passkey
4. Call this endpoint carrying `rawChallenge + userIntentJson + webauthnSignature`

**Payload Field Definitions**:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `userId` | string | Yes | User ID |
| `credentialId` | string | Yes | Passkey credential ID used to initiate the operation (for authentication) |
| `webauthnSignature` | object | Yes | WebAuthn assertion signature (see "WebAuthn Signature Format" above), challenge = intentHash |
| `rawChallenge` | string | Yes | Raw challenge value obtained from `/api/challenge` (base64url) |
| `userIntentJson` | string | Yes | User intent JSON string: `{ purpose, userId, credentialIdsToDelete }` |
| `credentialIdsToDelete` | string[] | Yes | List of Passkey credential IDs to delete (must match `userIntentJson.credentialIdsToDelete`) |

**`data` field (after JSON.parse)**:

| Field | Type | Description |
|-------|------|-------------|
| `success` | boolean | Fixed `true` |
| `deletedCount` | number | Actual number of Passkeys deleted |
| `accountDeleted` | boolean | `true` when no Passkeys remain after deletion (triggers cascade deletion) |

## 11. POST /api/tx/sign

Transaction signing. After authorization verification, the server signs the transaction with the private key inside the enclave.

Two modes are supported, distinguished by whether the `transaction` object contains a `rawTxHex` field:
- **Mode 1 (txParams)**: The platform provides structured transaction parameters; all fields are considered trusted
- **Mode 2/3 (rawTxHex)**: The platform provides raw transaction bytes; the server parses all auth-relevant fields from the raw bytes (does not trust explicit fields provided by the platform)

> **Important**: `authorizationJson` must be a **string** (without `webauthnSignature`); `webauthnSignature` is passed separately.
> The client computes the SHA256 hash of the `authorizationJson` string as the WebAuthn challenge, and the server computes the same hash to verify the signature.

**Payload Field Definitions**:

| Field | Type | Required | Description |

## 12. POST /api/key/import/init

First step of key import. Initializes a key exchange session, supporting two key exchange modes:

- **ECDH mode (default)**: Do not pass `rsaPublicKey`; the Enclave generates an ECDH key pair (prime256v1) and returns the public key. The client uses this public key to derive a shared key and then encrypts the private key for transmission.
- **RSA mode**: Pass `rsaPublicKey` (client RSA public key, PEM or Base64 DER); the Enclave generates a 256-bit AES key, encrypts it with RSA/PKCS1Padding (PKCS#1 v1.5), and returns it. The client decrypts the AES key with its own RSA private key and uses it for subsequent data encryption.

Supported RSA public key sizes: 1024, 2048, 3072 (automatically detected from the public key; no extra specification needed).

**Security Requirement**: Both steps of import mandatorily require the user's WebAuthn Passkey signature; the platform cannot silently import private keys without user authorization.

**Prerequisite Steps**:
1. Call `/api/challenge` (purpose=`key_import_init`) to get `rawChallenge` (pure random value)
2. Construct `userIntentJson = { purpose: "key_import_init", userId, importType }`
3. Compute `intentHash = SHA256(rawChallenge + userIntentJson)` and sign `intentHash` with Passkey
4. Call this endpoint carrying `rawChallenge + userIntentJson + webauthnSignature`

**Payload Field Definitions**:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `userId` | string | Yes | User ID |
| `importType` | string | Yes | Import type: `private_key` (raw private key), `mnemonic` (mnemonic), or `batch` (batch) |
| `rsaPublicKey` | string | No | Client RSA public key (PEM or Base64 DER). If passed, uses RSA mode; otherwise defaults to ECDH |
| `credentialId` | string | Yes | Passkey credential ID (base64url encoded) |
| `webauthnSignature` | object | Yes | WebAuthn assertion signature (see "WebAuthn Signature Format" above), challenge = intentHash |
| `rawChallenge` | string | Yes | Raw challenge value obtained from `/api/challenge` (base64url) |
| `userIntentJson` | string | Yes | User intent JSON string: `{ purpose: "key_import_init", userId, importType }` |

**`data` field (after JSON.parse, ECDH mode)**:

| Field | Type | Description |
|-------|------|-------------|
| `sessionId` | string | Session ID |
| `keyType` | string | Fixed `"ecdh"` |
| `enclavePublicKey` | string | Enclave ECDH public key (prime256v1, uncompressed hex, starts with 04) |

**`data` field (after JSON.parse, RSA mode)**:

| Field | Type | Description |

| `keyType` | string | `"rsa-1024"` / `"rsa-2048"` / `"rsa-3072"` |

## 14. POST /api/key/export/init

First step of key export. Initializes a batch key exchange session, encrypts multiple wallet data and returns them all at once. Requires WebAuthn signature confirmation. Supports two modes, both encrypt and return data at init time:

- **ECDH mode**: Pass `peerPublicKey`; the Enclave generates an ECDH key pair, derives the shared key to encrypt wallet data, and returns `enclavePublicKey` + `encryptedData`.
- **RSA mode**: Pass `rsaPublicKey`; the Enclave generates an AES-256 key to encrypt wallet data, encrypts the AES key with RSA/PKCS1Padding, and returns `encryptedAESKey` + `encryptedData`.
- One of `peerPublicKey` or `rsaPublicKey` must be provided; `rsaPublicKey` takes precedence.

**Batch Export Notes**:
- `exportInfo` is an array; each element specifies a `walletId` and the `addresses` to export
- When `addresses` is an empty array, exports **all** private keys under that `walletId`
- When `addresses` has values, each element can be:
  - A plain address string `"0x..."`: exports the private key for that address on all chains
  - An `{address, chainId}` object: precisely exports the private key for the specified address on the specified chain (the same address on different chains can be exported separately)
- All wallet data is encrypted into a single JSON object and returned at once; only one WebAuthn signature is required

**Prerequisite Steps**:
1. Call `/api/challenge` (purpose=`key_export`) to get `rawChallenge` (pure random value)
2. Construct `userIntentJson` (ECDH: `{ purpose, userId, exportInfo, peerPublicKey }` or RSA: `{ purpose, userId, exportInfo, rsaPublicKey }`)
3. Compute `intentHash = SHA256(rawChallenge + userIntentJson)` and sign `intentHash` with Passkey
4. Call this endpoint carrying `rawChallenge + userIntentJson + webauthnSignature`

> **Note**: `peerPublicKey`/`rsaPublicKey` must be included in `userIntentJson` to prevent man-in-the-middle substitution of key exchange parameters. `exportInfo` must also be included in `userIntentJson` to prevent the platform from substituting the export scope.

**Payload Field Definitions**:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `userId` | string | Yes | User ID |
| `credentialId` | string | Yes | Passkey credential ID |
| `webauthnSignature` | object | Yes | WebAuthn assertion signature (see "WebAuthn Signature Format" above), challenge = intentHash |
| `rawChallenge` | string | Yes | Raw challenge value obtained from `/api/challenge` (base64url) |
| `userIntentJson` | string | Yes | User intent JSON string (includes exportInfo, peerPublicKey or rsaPublicKey) |
| `exportInfo` | array | Yes | Export info array (must match `userIntentJson.exportInfo`) |
| `peerPublicKey` | string | Required for ECDH | Client ECDH public key (hex, uncompressed starting with 04); choose one of `peerPublicKey` or `rsaPublicKey` (must exactly match `userIntentJson.peerPublicKey`) |
| `rsaPublicKey` | string | Required for RSA | Client RSA public key (PEM or Base64 DER); choose one of `peerPublicKey` or `rsaPublicKey` (must exactly match `userIntentJson.rsaPublicKey`) |

`exportInfo` array element fields:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `walletId` | string | Yes | Wallet container ID |
| `addresses` | array | Yes | List of addresses to export. Empty array means export all private keys under that walletId. Elements can be: plain address string (all chains) or `{address: string, chainId: number}` object (exact chain match) |

**`data` field (after JSON.parse, ECDH mode)**:

## Appendix B: Write Operation Flow (Requires WebAuthn Signature)

The following write operations require **two steps** (using `wallet_create` as an example):

**Step 1**: Call `/api/challenge` to get `rawChallenge` (pure random value)

```json
// payload
{
  "purpose": "wallet_create",
  "userId": "user-xxx",
  "credentialId": "cred-xxx"
}
// response data
{
  "challenge": "rawChallenge_base64url",
  "userId": "user-xxx",
  "expiresAt": "2026-04-06T06:00:00.000Z"
}
```

**Step 2**: The client constructs `userIntentJson`, computes `intentHash`, signs with Passkey, then calls the write operation endpoint

```
userIntentJson = JSON.stringify({ purpose, userId, chains, ... })
intentHash = SHA256(rawChallenge + userIntentJson)
webauthnSignature = Passkey.sign(intentHash)
```

```json
// payload (wallet/create example)
{
  "userId": "user-xxx",
  "credentialId": "cred-xxx",
  "rawChallenge": "rawChallenge_base64url",
  "userIntentJson": "{\\"purpose\\":\\"wallet_create\\",\\"userId\\":\\"user-xxx\\",\\"chains\\":[{\\"chainId\\":\\"1\\"}]}",
  "webauthnSignature": {
    "authenticatorData": "base64url_authenticator_data",
    "clientDataJSON": "base64url_client_data_json_with_intentHash",
    "signature": "base64url_der_signature"
  },
  "chains": [{ "chainId": "1" }]
}
```

> **Business Endpoint Verification Logic**:
> 1. Query the challenge record by `rawChallenge`; reject if it does not exist (replay protection)
> 2. Compute `intentHash = SHA256(rawChallenge + userIntentJson)`
> 3. Verify WebAuthn signature (`expectedChallenge = intentHash`)
> 4. Parse `userIntentJson` and compare fields one by one with actual business parameters (prevent platform parameter substitution)
> 5. Consume (delete) the challenge record

**Security Guarantees**:
- `intentHash = SHA256(rawChallenge + userIntentJson)` binds randomness (replay protection) and business semantics (parameter tamper protection) together
- The platform cannot substitute business parameters after the user signs, because any modification would cause intentHash mismatch
- `rawChallenge` ensures each challenge is unique, preventing replay attacks
- Parameters in `userIntentJson` must match actual business request parameters; the server compares field by field

## Appendix E: Account Freeze Mechanism

### Trigger Conditions

When an existing account (userId exists) binds a Passkey via `/api/passkey/register/complete` Scenario A (no Passkey, purpose=register), and the account has at least one wallet (mnemonic wallet or raw private key wallet), the account is automatically frozen.

**Conditions that do not trigger freeze**:
- Brand-new user (userId does not exist)
- Existing account but no wallets
- Scenario B (existing Passkey, adding a new Passkey)

### Freeze Rules

> **Core Principle**: Freeze does not automatically lift. After the freeze period expires, a signed request must be made using the Passkey bound at freeze time; only after the request succeeds is the freeze permanently lifted. Otherwise, the account remains frozen.

**Freeze Duration Configuration** (highest priority first):

| Source | Config Path | Description |
|--------|------------|-------------|
| Smart contract | `runtimeParams.security.freezeDurationSeconds` | Contract config, highest priority |
| Environment variable | `FREEZE_DURATION_SECONDS` | Used when contract is not configured |
| Code default | - | 259200 seconds (72 hours) |

| Phase | Time Range | Behavior |
|-------|-----------|----------|
| Freeze period | Within configured duration after freeze starts (default 72 hours) | **All requests** for this userId are rejected (HTTP 403) |
| Unfreeze condition period | After freeze period expires | Only requests with `webauthnSignature` using the Passkey bound at freeze time (matching credentialId) are allowed; unsigned requests are still rejected |
| Unfreeze | After freeze period expires, a signed request using the bound Passkey succeeds | Permanently lifts the freeze; all endpoints return to normal |

**Detailed Rules After Freeze Period Expires**:

| Request Type | credentialId Match | webauthnSignature | Result |
|-------------|-------------------|-------------------|--------|
| Any | No match | - | Rejected (403) |
| Any | Match | None (e.g. `/api/challenge`, `/api/wallet/list`) | Rejected (403) |
| Any | Match | Present | Allowed; permanently lifts freeze after success |

### Exempt Endpoints

The following endpoints are not affected by account freeze and can be called normally even when the account is frozen:

| Endpoint | Description |
|----------|-------------|
| `/api/enclave/info` | Enclave info query (no authentication required) |
| `/api/admin/userId/list` | Admin user list (platform signature) |

### Freeze Response Format

Requests rejected during the freeze period return HTTP 403:

```json
{
  "error": "Account is frozen: new passkey bound to existing account with wallets, account suspended until 2026-04-11 12:00:00"
}
```

Requests without webauthnSignature after the freeze period return HTTP 403:

```json
{
  "error": "Account is frozen: passkey signature required to unfreeze account"
}
```

Requests with non-matching credentialId after the freeze period return HTTP 403:

```json
{
  "error": "Account is frozen: request must use the passkey that was bound during registration to unfreeze account"
}
```

### Registration Endpoint Freeze Response

When `/api/passkey/register/complete` triggers a freeze, the registration itself still succeeds (Passkey is bound), but the response includes freeze information:

```json
{
  "success": true,
  "userId": "user-xxx",
  "credentialId": "cred-xxx",
  "isFirstPasskey": true,
  "frozen": true,
  "freezeUntil": "2026-04-11 12:00:00"
}
```

### Security Design Rationale

This mechanism is designed to prevent the following attack scenario:

1. An attacker learns a user's userId
2. The user created an account through platform batch import (has wallets but no Passkey)
3. The attacker exploits Scenario A's "existing account Passkey binding" feature to bind their own Passkey
4. The attacker uses the bound Passkey to access the user's wallet assets

The freeze period (default 72 hours, configurable via contract or environment variable) provides a time window for the user and platform to discover the anomaly and take action. After the freeze period expires, only a signed request using the Passkey bound at freeze time can lift the freeze, ensuring that the Passkey holder's asset access rights are protected. The freeze does not automatically lift over time — a signed request must be actively made to verify Passkey ownership before the account can be restored.

### Frozen Account Passkey Replacement

When an account is in a frozen state, re-registering a Passkey via `purpose=register` is allowed. This mechanism provides a dispute buffer period for the true account owner:

**Replacement Flow**:
1. Call `/api/challenge` (`purpose=register`) to get a challenge (frozen accounts allow this purpose)
2. Create a new Passkey
3. Call `/api/passkey/register/complete` to submit the registration

**Replacement Effects**:
- The old frozen Passkey is deleted
- The new Passkey is registered
- The freeze timer resets from the current moment (default 72 hours, configurable)
- The frozen credentialId is updated to the new Passkey's credentialId

**Design Purpose**: If the previous registration was fraudulent, the true account owner can re-register. Each re-registration extends the freeze period, providing more buffer time for dispute resolution rather than forcing an unlock after expiration.

**Limitations**:
- Frozen accounts are not allowed to use `purpose=register_passkey` (because the frozen Passkey's signature cannot be verified)
- After replacement, the account remains frozen; the new freeze period must expire before a signed request can lift the freeze
